2026-11-23 用户最终确认“每天轻扫＋每周集中研究”，并明确热点为额外工作量，保留既有安排。热点扩词去重后，合格项以P0接入制作、审批、发布与效果复查；博客仅写入Flatkey blog和ModelFit blog。原常规计划和额度不变，额外热点逐项留账，不另建热点job，不新增付费、外部发送或产品代码权限。

## 每日轻扫与每周集中研究

沿用每日北京时间10:30的 `seo-10-00`：每天含周末轻扫新事件、事实及独立需求，保存覆盖、原始事件时间和候选；不每天重复完整扩词和SERP研究。每周一在同一入口集中扩词、聚类、完整去重及Top10／前5逐页3C研究，遇非工作日顺延首个实际工作日。本次手工批次计入2026-11-23周集中研究，按原周一存储桶与稳定批次键复用，不再跑一整批。已核验且时效紧迫的热点可在实际工作时段立即补齐完整研究，不必等下周。制作、送审与发布仍守中国官方实际工作日和原业务时段；原技术巡检与每日到期效果复查职责保留，各自如实记录完成状态。

- 每日检查最近 24 小时内的新事件，以及最近 7 天有真实升温证据的主题；最近 30 天只作需求、内容和热度的比较基线。模型／硬件版本发布、推理或部署能力变化、公开 GPU 报价及供应商／地区变化等，应与本站实际业务和可承接内容相关。
- 事件事实优先读实际厂商、模型／硬件维护者、公开发布说明、模型卡、官方文档或原始报价页。另读取与事件匹配的独立需求信号，例如目标市场真实搜索趋势、近期具体搜索问题或独立社区讨论。工具建议、转载、标题或 AI 摘要不能代替实际来源。
- 记录原始事件发生／版本发布时刻，或真实升温开始时刻、来源发布时间及实际读取时刻；区分事件与升温两种依据。重新发现旧新闻、转载日期变化、网页抓取时刻和当前扫描日期不能把旧事件重新算作近期热点。
- 需求有数字时保存来源、市场语言、时间窗、基线及实际变化；只有讨论证据时保存具体问题、原帖时间和限制，不能写成已测搜索量暴增。无搜索量或工具尚未收录不是零需求；新模型／新词先保留补证，不因此自动清退。
- 官方事实和独立需求均实际核验后才标记“已核验热点”。传闻、日期未知、未来事件、来源无法读取、需求尚未核实或已超过有效期时，保存具体待补内容，不伪写核验通过。

使用已有且获授权的搜索和关键词渠道，账户偏好沿原规定。不得绕验证码、登录或付费限制，不启用暂停中的 DataForSEO，不扩大原付费查询、分页、国家或预算。缺某个渠道先用已有授权替代渠道补证，并保留实际覆盖；未完整检查时不能写“暂无热点”。全部预定来源完成且无合格结果时才写“暂无合格热点”，不为凑日交付新建任务。

## 扩词、意图与完整去重

以真实实体、型号／版本和用户问题扩展主词、相关实体词、问题词及意图簇。可研究价格、对比、部署、显存、配置、可用性等实际需求，但不能把通用模板组合当作已验证关键词。每词分别核实目标市场及语言；同词不同市场的证据不互相替代，流量增长不自动改变制作语言。

每个热点先读完整活跃词库与 TopicMap、全量相关任务／issue／计划、CMS 全部状态、已发／草稿／预留意图、官网路由／sitemap／canonical 和可用 GSC 词页证据，再作以下决定：

| 核查结果 | 承接方式 |
| --- | --- |
| 已有任务覆盖同站、市场语言、意图和具体问题 | 沿原 taskId／issue 增补热点与研究证据，继续原会话及原版本，不复制任务 |
| 已有页面能够承接 | 优先更新原 URL 和原基线，不因换词或热点新增同意图页 |
| 没有合适任务，有真实独立需求但研究尚未齐备 | 经现有接口创建 `kind=research|review`、`status=planned` 候选及关联 issue，并保存待补门槛 |
| 独立新内容研究完整合格 | 博客按本次明确的额外目标接入Flatkey或ModelFit；其他类型仍按原站点资格和额度，不替换常规任务 |
| 身份冲突、证据缺失或范围外 | 保存具体冲突／缺口／排除原因，不编造身份或另建替代任务 |

事件身份以真实实体／版本、事件类型和原始事件／升温身份稳定表达，不能加入日报日期、扫描时间或报告 ID 来每日新建同一热点。任务去重仍以同站、市场语言、页面／意图及具体问题为准；同一事件在不同站点的独立需求分别核实，不能因共享热点跨站迁移任务。一个页面的共同问题可以关联多个真实词，不按每个副词生成一页。暂停、撤回及范围外的原任务不因热点恢复。

正式制作前，原词、原市场、原语言的一套 10 条自然结果、前 5 条实际打开的逐页 3C、完整去重和真实关键词／TopicMap 身份仍须齐备；六项分析与 E-E-A-T 按[执行研究与补证规范](seo-execution-research.md)执行。Ahrefs 不足时先用已有授权当地搜索或正常浏览器补证，不换词、拼市场或用摘要凑结果。热点只提高补证顺序，不降低门槛。

## 在既有记录保存最高优先级

现有 issue 有 `priority` 字段，真实匹配的热点 issue 使用 `priority=P0`。task、Topic 及 brief 没有通用 priority 字段，不新增虚构字段，不宣称已改变不存在的字段。task 的最高优先级通过现有 `evidence` 与中文 `nextAction` 保存，并由执行排序实际消费。

优先在原任务 `evidence` 保存两条已实际核验的记录，分别表示官方事实及独立需求；本地排序同时读取既有 `task.evidence`、`task.brief.evidence` 与 `task.research.evidence`。`label` 使用下列固定格式，尖括号是说明，不是可直接入库的真实证据：

```text
seo-hotspot-v1;event=<稳定事件ID>;at=<真实事件或升温ISO时间>;basis=event|rise;role=official|demand;verified=1
```

两条的 `event`、`basis` 和 `at` 所指的真实时刻必须一致，`role` 分别为 `official` 和 `demand`；每条使用自己实际来源的 HTTPS `url` 与真实 `observedAt`。官方来源和需求来源使用不同 URL，去掉 fragment／常见 UTM 等追踪参数后仍须不同，优先选独立主机；同篇官方材料换标题、锚点或镜像不构成独立需求。只有实际打开并核验内容的人／执行会话才能写 `verified=1`，格式正确本身不证明来源真实或研究合格。

事件／升温时刻及两条读取时刻均不能在未来，读取不能早于事件／升温，且当前距事件／升温及读取均不超过 7×24 小时（恰好 7 天仍有效）。每天重新核验热点是否仍成立；仅把 `observedAt` 改成今天不能延长旧事件有效期。超过有效期时停止其热点优先资格，保留证据与原任务；原 issue 的 P0 若仅因热点设置，以版本校验恢复原有优先级或保存当前普通优先判断，保留 before／after，不能覆盖其他仍成立的独立紧急依据。确有新的升温事实时增加真实新证据后再评估，不能刷日期维持永久 P0。

中文 `nextAction` 保留原文前缀，追加“已核验近期热点、最高优先级”、具体缺口和下一步，并引用同一事件及来源产物。每条证据须满足现有 schema 的 label、URL／artifact、时间和数组容量限制；不能扩字段或截断原证据腾空间。空间不足明确记未应用并保留待同步产物。

候选、issue、原任务、研究及计划写入均沿已有接口、稳定 requestId 和 `expectedVersion`，保留原主词、市场语言、原 ID、weekStart、dueAt、状态、稿件、分支、审批、租约与历史。冲突重读后再算；响应不明先读回，不能换 ID 盲重发。每次逐项生产读回确切 ID、版本、新增 evidence 和 issue.priority；跨记录写入不是一次原子事务。

## 研究、排期与执行排序

最高优先级贯穿热点补证、关键词研究、候选选择、正式排期和合资格任务领取。在各阶段先筛选原资格，再将有效热点排在普通任务前；有效热点之间按原 dueAt、稳定 taskId 排序。未核验、未来、过期及证据不完整的标记不能获得热点优先权。

本地领取使用 [`scripts/lib/seo-hotspot-priority.cjs`](../scripts/lib/seo-hotspot-priority.cjs) 的 `activeHotspotPriority(task, now)` 识别上述证据、真实时间和有效期，并在 `dueTasks` 完成原资格过滤后排序。该 helper 只检查现有元数据与双来源结构，不代替官方身份、实际需求、搜索研究或发布资格核验。

研究候选不等于已经取得制作资格。每日发现会话实际继续补证并交接原研究，只有研究合格且原正式计划或真实用户额外目标资格、执行类型均合法的内容任务才能交执行器制作；不能假定 `kind=research|review` 自然成为博客制作任务。已有相应制作任务时沿原 taskId 复用；确无制作任务时，可按现有 schema 新建一个依赖原研究的单一制作任务，使用实际支持的 `blog`、`optimization`、`landing` 或 `cluster` 等类型并匹配本站执行 scope。研究与制作是可关联的不同阶段，不能每日各建一套，也不能以此替代失败、延期或已排原任务。研究产物、真实关键词身份与热点 evidence 须传入制作任务并生产读回，不改产品接口或伪造 task.kind 绕过校验。

本次用户明确“额外增加一些工作量，但是不去改变既有的安排”。常规47项、两个原Monday计划及其taskIds／targets／版本按实际记录保留，不用“原额度已满”阻挡本次额外热点，也不提升原常规配额、强替任务或新建同周plan。系统会选择同周最新计划，新plan可能遮住旧任务，因此不能用它作为额外账本。

研究合格后，经既有正常登录用户内容接口登记真实用户明确的 `kind=blog` 额外目标及原研究依赖，保留本次授权、本站keyword身份、完整研究、热点证据、确切稿件版本及生产读回。平台现有真实human目标资格可独立于原plan；必须由真实已认证用户入口保存，不能让collector伪造human、改task.kind、提权或绕认证。接口／身份不可用则继续完成制稿与素材，保存具体待同步依赖，不假报已接执行器。原研究不改成博客、不迁站；已有制作任务则复用，无匹配才建立一个相应阶段任务。本批共三个独立源文：ModelFit Inkling、ModelFit RTX/DGX、Flatkey MoE；MoE原ModelFit研究保留，Flatkey另核本站身份、内容能力及去重，不机械再做同题ModelFit文章。

额外热点单独核对数量、原taskId、研究、语言、交付及实际发布，不重复占用常规新增名额；本次授权不等于无限付费或免除研究／审批／发布校验。不强替／取消正式或在途任务，不中断租约，不复制延期，不改原dueAt，不提前未来日任务。其他延期继续原补齐规则；热点过期不自动续热。

## 效果复查与每轮回执

在原任务保存上线／优化前基线及发布事实，以真实上线日登记 7／14／28 天到期复查，不每轮另建同一问题。比较同页／查询／国家／来源的可比曝光、点击、排名、自然搜索访问和注册；缺完整窗口、未收录或来源延迟如实保留，不能补零、承诺排名或把热点上涨全归因于新页面。热点过期不抹除原任务的后续效果复查。

每日轻扫／每周集中研究分别保存覆盖与批次状态；完整内部回执至少包含：检查时间与覆盖来源、真实事件与热度依据、关键词／意图簇、完整去重对象及结果、复用／新建的生产 taskId 和 issueId、最高优先级证据、研究缺口、原计划保持情况与额外热点数量／资格、实际制作／待审／发布状态、效果复查日期及具体失败原因。未发现合格热点、追踪未完成、候选待研究、已入正式计划及实际上线分别记录。

对用户及日报周报的优先关注最多 3 项，每项一句并链接真实任务，完整说明留任务详情。沿原报告对应位置表达，不新增重复板块或改变统计口径；周报仍先审核确切全文后发送，周四日报只归档且不补发。任何自动化配置读回、测试通过或文档更新，只说明流程已接好；发现、入库、制作、审批、发布和效果必须分别以真实运行回执验收。
