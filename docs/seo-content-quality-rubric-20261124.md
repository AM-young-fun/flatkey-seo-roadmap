# 日常内容质量、专业可信度与结构化数据规范

本规范是用户在批准完整流程v9后的日常执行要求，适用于授权范围内的研究、博客/页面制稿、旧文翻新、优化与发布验收。由AI在后台完成自审和真实修正，不新增定时任务或重复工作单。仍保留原任务ID、实际交付日、审批、内容版本和有效租约；全部相关自动化仍暂停，规则更新不代表已恢复或已逐页检查。原Prompt素材任务的提示词和目标不改。

## 用户给出的16个原始问题

以下问句完整保留。每项须写实际回答和证据，不能一律填“是”：例如第10和16题发现错误应先修正；第14题没有独立权威证据时如实说明，不编造声誉。

### 与内容和质量相关的问题

1. 内容是否提供了原创的信息、报告、研究或分析？
2. 内容是否提供了对主题的实质性、完整性或全面性描述？
3. 内容是否提供了富有洞察力的深刻见解或有趣信息？
4. 如果内容借鉴了其他来源，它是否避免了简单地复制或改写那些来源，而是提供了实质性的额外价值和原创性内容？
5. 主标题或网页标题是否对内容进行了非常实用的描述性总结？
6. 主标题或网页标题是否避免了夸大其词或耸人听闻？
7. 您会将这种网页添加为书签、分享给朋友或推荐给他人吗？
8. 您觉得这样的内容会出现在印制的杂志、百科全书或书籍中或被它们引用吗？
9. 与搜索结果中的其他网页相比，此内容是否具有实质性的价值？
10. 内容是否有拼写或样式问题？
11. 内容是制作精良还是貌似草率或制作仓促？
12. 内容是否是由或外包给很多创作者共同创作而成，或者是否已在大量网站中广泛传播，以至于个别的网页或网站没能获得同等程度的注意或关注？

### 与专业知识相关的问题

13. 内容呈现信息的方式是否会让您愿意信任它？例如明确的来源、所涉专业知识的论据、对作者或发布网站的简介（例如提供指向作者页面或网站中自我介绍页面的链接）？
14. 如果有人研究了内容的制作网站，那么他们的印象是否是该网站深受用户信任或被公认为相关主题的权威？
15. 这些内容是否由对相关主题非常了解的专家或爱好者撰写，或是否经过了此类人员的审核？
16. 内容是否存在任何可以轻松验证的事实错误？

## 研究、改稿及复审闭环

| 阶段 | 必须完成的工作 | 原任务保存内容 |
| --- | --- | --- |
| 研究与制稿自审 | 原词、原市场语言、搜索意图、现有Top10及前5实际页面研究/全量去重沿原标准；逐项回答16问，明确相对当前SERP的独有贡献、实用价值和事实缺口 | 原始来源、观察时间、比较页面、16项回答、问题定位、实际待改内容和当前contentVersion |
| 改稿 | 修正事实、标题、范围、内容缺口、推理、结构、语言、作者/引用、图片及标记；不能只修改检查表 | 每项改前/改后或diff、真实来源、实际修正时间、内容hash和新contentVersion；未改成的具体原因 |
| 发布前复审 | 对确切待发版本重新检查16问与研究结论，并核最终预览HTML中的链接、图片和Schema；版本或关键事实变更后重做相关复审 | 同一contentVersion的复审结果、证据artifact、最终URL/canonical、真实修正、尚未解决的阻断项 |
| 发布后匹配版本验收 | 仅在原发布权限和审批条件通过后，读最终公开SSR HTML并核实真实版本、HTTP状态、canonical、语言、nofollow/alt/Schema与页面实际内容 | 原taskId、publicationId、contentVersion、上线/验证时间、HTML/DOM证据及hash；不能拿草稿、旧版本或另一语言替代 |

这些是日常自审和验收，不额外创造人工审批点；原已有发布审批、付费、重大方向和Google/产品变更边界继续有效。无法核实的经历、作者、测试、价格或产品事实不填假通过。缺研究或事实时先沿原任务补证，不换词凑证据、不重复付费。自然变化归因仍按用户最新简化：无可对应的真实动作直接写“自然变化”，不为它自动建整改任务。

## 每篇应达到的实际质量

- 给出可指出位置的原创价值：真实分析、复算、可用步骤、判断条件、对比、工具或案例；只改写其他页面不算独有贡献。区分实测、来源数据、复算和假设，未实际测试不写成实测。
- 围绕当地用户的实际问题完整回答，解释限制、适用条件和取舍。相对SERP说明具体补足了什么，不以字数、篇数或同义反复代替信息量；标题准确实用，不夸大或制造惊讶。
- 修正拼写、代码示例、段落结构、易读性及本地语言表达；译文复审本地标题、摘要、正文和章节，不机械沿用不相干市场术语。
- 数字、年份、价格、产品能力和关键事实有可核查原始来源与日期。优先官方原始文档和真实证据，引用须支持当前具体结论；不造专家、资历、审阅、经验、测评、口碑或用户证言。
- 作者、负责团队、网站介绍和审阅者仅使用可核实身份；有真实页面才链接。新站缺少外部认可如实记录，不能为了回答第14题而捏造权威或广泛信任。
- 批量AI生产逐页复查意图、事实、独有贡献及质量，不因同模板或同话题而省略单页关注。重复意图先补原页/复用原任务，不用大量薄页抢占配额。

## 同话题博客互链

- Flatkey 和 ModelFit 的新博客按本站 TopicMap 主话题核对已上线文章。源文及每个译文各自选择同语种的相关博客，优先链接能帮读者完成下一步的一至三篇。锚文本放在相关正文段落，说明目标内容。一个话题只有一篇合格文章时，记录缺口，后续有适合页面时补齐。
- 制稿和发布前读候选规范 URL，核 HTTP、最终地址和正确语种。使用同站正式链接，复用正文已有链接。导航、推荐栏或只有模板输出的链接不能代替正文链接。
- 新文正式 URL 验收后，借原博客发布入口给已选旧文补向新文的正文回链。先读 CMS 当前语言版本、原正式页面和有效工作绑定。回链改动保留旧页原正文、首发日期、SEO 元数据、其他链接和各语种状态。页面在途或版本冲突时沿原记录待补，已验收的新文仍如实记发布状态。
- 两个方向逐向读取最终正式 HTML，确认可访问、canonical、语言及正文实际链接。随原任务保存双方 URL、链接锚文本、受改版本和观测时间。缺失方向留明确待补结论，已完成回链不重复发版。

## Schema Markup按真实页型落地

| 实际页面 | 标记口径 | 必须匹配的事实 |
| --- | --- | --- |
| Flatkey博客 | `BlogPosting` | 真实标题、正文摘要、URL、作者/团队、图片及真实首发/实质更新日期 |
| ModelFit技术文章 | `TechArticle` | 技术主题、实际步骤/说明、真实标题/作者/日期；不能给普通营销文伪装技术测试结论 |
| 一般页面及导航层级 | `WebPage`、`BreadcrumbList` | 当前canonical URL、实际名称和用户可见层级/导航路径 |
| 真实可运行工具 | `WebApplication` | 实际工具名称、用途、URL及可使用功能；不能把静态文章或尚未实现的功能说成应用 |
| 真实产品/价格内容 | 按页内容使用 `Product`/`Offer` | 页面真正展示的产品、供应/报价、币种、价格、可用条件和来源日期；无价格不造价格，不给所有文章套产品/报价 |
| 真实问答 | 仅在存在用户可见或可正常展开的真实问答时使用 `FAQPage` | 每个问题、答案与页面实际可见内容一致，不为了标记另造隐藏问答 |

禁止捏造Review、AggregateRating、评分、评论、专家身份、库存或购买承诺。已有Organization/作者引用须真实，实体与页面URL一致；同页多节点可合理关联，但不能输出重复或冲突的同一实体。结构化数据与主内容一致且可访问，也不保证Google展示富结果。[Google结构化数据政策](https://developers.google.com/search/docs/appearance/structured-data/sd-policies)要求内容与标记相符；类型语义参考[BlogPosting](https://schema.org/BlogPosting)、[TechArticle](https://schema.org/TechArticle)。

Schema现状如实记录为“已有部分实现，尚未逐页全量验收”。本规范建立了后续执行与复查门槛，不能据此声称全部站点或历史页面已完成。

## 最终SSR HTML联合验收

1. 读取该实际页面、该语言、该内容版本的最终SSR响应HTML，检查HTTP、canonical和可访问性；需要浏览器时也核实际DOM。只验React源码、Markdown或CMS字段不算最终通过。
2. 所有外链最终 `a[rel]` 含 `nofollow`，保留已有必要 `noopener`/`noreferrer`，不误改内链。所有最终 `img` 显式有alt：内容图准确描述真实图片，纯装饰图 `alt=""`，不塞不相干关键词。
3. 解析实际 `application/ld+json`，核JSON有效、类型正确、字段/实体/canonical/作者/日期/图片与可见内容一致，无冲突Schema或虚假产品、问答、评分。解析成功不等于事实验收通过。
4. 保存实际检查数量、错误元素/字段、改前/改后和验证结果。检查未完成写“检查未完成”；来源或页面未到可验窗口如实保留，不伪报“暂无问题”。不因验Schema擅改GSC/Google设置或提交新索引操作。

## 原任务证据保存

逐阶段保存独立artifact，内容至少包含原taskId、页面/语言、contentVersion、内容/HTML hash、评审时点、16问逐项实际回答与证据、问题定位、真实修正diff、复审结果，以及最终nofollow/alt/Schema检查。artifact是证据文件，不是给Task虚构新字段。

通过原已支持的 `evidence`/`nextAction` 保存artifact引用与该版本说明，沿原expectedVersion及稳定requestId写入并CAS读回；未知响应先读回、不盲重发。旧证据和旧contentVersion保留，不回写伪造历史通过。发现同一页同一问题先复用原task/issue；质量复审不是重复制作任务，也不重开已完成交付run。

## 面包屑结构化数据（用户指定Google官方规则）

按用户提供的[Google BreadcrumbList官方指南](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb?hl=zh-cn)描述真实典型用户导航路径；不机械照URL层级造路径，不把所有页的末项写成首页。至少2个`ListItem`，每项有实际名称`name`和从1连续递增的`position`；前项`item`是该实际导航目标的完整URL，末项当前页的`item`可以省略。动态模型、硬件、工具和文章使用该页真实名称、路径及同站canonical，不重复输出冲突列表。

导航和JSON-LD在服务端共用路径与标题，保留用户实际可见的导航及原样式；仅有首页单节点不造列表。验最终SSR HTML中解析后的完整列表、节点数量、真实URL和内容版本，并用Google Rich Results Test等验证工具核验；测试通过不保证出现富结果。GSC/Google保持只读，不因此请求索引、改权限或更改配置。
